# Architecture

## Request pipeline

1. **Conversation memory** loads the most recent bounded history from SQLite.
2. **Intelligence Router (LLM 1)** returns a Pydantic-validated JSON route: `GENERAL_CONVERSATION`, `BUSINESS_KNOWLEDGE`, `MIXED`, or `CLARIFICATION_REQUIRED`. Application code overwrites the model's RAG/grounding flags to match the route invariant.
3. **General route** calls the answer model directly with history and the current message. The service branch does not call the retriever.
4. **Business/mixed route** rewrites follow-ups into a standalone retrieval query, generates a query vector through the remote Gemini Embedding API, queries the persistent Chroma collection, de-duplicates results, and bounds context size.
5. **Evidence evaluation** uses the answer model to classify retrieved coverage as sufficient, partial, insufficient, or conflicting.
6. **Answer generation** uses the same answer model. Mixed requests allow general explanation while requiring evidence for organization-specific facts.
7. **Grounding verification** uses the answer model to evaluate business factual claims and actual source IDs. One correction/re-verification cycle is allowed. If verification remains uncertain, the service returns a source-limited fallback rather than unsupported claims.
8. **Persistence** stores the user and assistant turns, including citation metadata, in SQLite.

## Persistence

- `data/assistant.db`: conversations, ordered messages, citations, and ingestion file hashes.
- `data/chroma/`: Chroma persistent vector collection, one collection for the prototype workspace.
- `knowledge/`: user-supplied documents; no fabricated business facts are shipped.

## Ingestion

Supported parsers extract text from TXT/Markdown, PDF, DOCX, CSV, and JSON. Text is chunked by paragraph with bounded overlap. Every vector record stores filename, relative path, SHA-256, chunk ID/index, page (or -1 if unavailable), title, and ingestion timestamp. Unchanged hashes are skipped, modified files are replaced, and deleted files are pruned. A corrupt file is logged without stopping other files.

The source folder is resolved before scanning; symlinks and resolved paths outside the knowledge root are skipped. Retrieved text is explicitly marked as untrusted reference data in model prompts.

## Security boundaries

- LLM and Gemini embedding API credentials only come from environment variables / `.env`; secret values are not logged or returned by APIs.
- Knowledge document text is sent to Google's Gemini Embedding API for vector generation; only index documents that are appropriate to transmit to that provider.
- `.env` and local data are git-ignored.
- The server binds to `127.0.0.1` by default.
- User-provided knowledge is not an instruction source.
- Session IDs are isolated in SQLite. The prototype is intended for one local operator and does not include authentication or tenant security.
- No model chain-of-thought, prompts, or internal verifier trace is exposed in the UI.

## Known architectural constraints

- Retrieval vectors are generated by Google's `gemini-embedding-001` API using `RETRIEVAL_DOCUMENT` for indexed chunks and `RETRIEVAL_QUERY` for user queries. The output dimension defaults to 768 and vectors are normalized before storage/search.
- The app initializes a lightweight API client at startup; it does not load local PyTorch or Sentence Transformers model weights. Knowledge ingestion and retrieval still require Gemini API access.
- The Chroma collection name is versioned (`business_knowledge_gemini001_768`) so vectors from the previous local embedding model are not mixed with Gemini vectors. Re-index knowledge after migrating.
- Image-only/scanned PDFs are not OCR processed.
- LLM 2 is reused for evidence assessment, answer generation, correction, and verification, as requested; this trades additional latency for a strict two-model configuration.
